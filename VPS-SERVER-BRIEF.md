# Сервер: что это, чем занят, сколько осталось

Файл для чата, который будет ставить на этот сервер ещё одного бота.
Все цифры сняты с живой машины **01.10.2026**, аптайм на тот момент — 8 дней.

**Короткий ответ: места полно.** Журнал занимает примерно одно ядро из четырёх и
1.6 ГБ из 24. Второй бот — особенно если он без браузера — поместится с огромным запасом.
Но есть два ограничения, которые надо знать заранее (раздел «Чего нельзя»).

## 2. Чем занят сейчас

Шесть служб. Все слушают только `127.0.0.1`, наружу открыт **только SSH**.

| Служба | Что делает | Память |
|---|---|---|
| `trade-bot` | телеграм-бот журнала сделок, long polling | 56 МБ |
| `tv-worker` | HTTP-съёмщик скринов, `127.0.0.1:3100` | 92 МБ |
| `tv-browser` | постоянный Chromium с живой сессией TradingView | 72 МБ * |
| `xvfb` | виртуальный экран `:99` для браузера | 81 МБ |
| `x11vnc` + `novnc` | доступ к этому экрану, нужен раз в полгода для входа в TradingView | 55 МБ |

\* в счётчике службы только обёртка: snap запускает Chromium в отдельном сеансе,
и его процессы (11 штук, вместе около 1.7 ГБ RSS) в cgroup службы не попадают.

### Сколько это реально ест

```
Процессор   занято 16% времени с момента загрузки (из 4 ядер)
            в покое: 0.7 ядра из 4, из них почти всё — Chromium
            load average 0.57 / 0.60 / 0.71
Память      1.6 ГБ занято, 16.7 ГБ свободно, 5.9 ГБ под кэшем
Диск        6 ГБ из 45 ГБ (14%)
Логи        83 МБ всего journald
Трафик      2.6 ГБ входящего, 1.1 ГБ исходящего за 8 дней
            (лимит Oracle — 10 ТБ в месяц, то есть не упрёмся никогда)
```

**Откуда берётся это одно ядро:** открытый график TradingView непрерывно получает тики и
перерисовывается. Это не пики, а ровный фон. Съёмка скринов (несколько раз в день,
по 90 секунд) добавляет сверху, но на фоне четырёх ядер незаметна.

### Свободно для нового бота

- **~3 ядра** — но см. оговорку про всплески ниже
- **~20 ГБ памяти**
- **~39 ГБ диска**
- порты: заняты `22`, `3000`, `3100`, `5900`, `6080`, `9222`, `111`, `631`.
  Бери любой свободный и **слушай на `127.0.0.1`** — наружу всё равно закрыто фаерволом Oracle.

## 3. Чего нельзя

**1. Второй бесплатной машины не будет.** Oracle Always Free даёт на весь аккаунт
**4 OCPU и 24 ГБ** ARM-мощностей, и эта машина забрала всё. Либо новый бот живёт здесь же,
либо надо разносить эту машину на две по 2 ядра — что означает переезд журнала и ручной
повторный вход в TradingView через VNC. Не стоит того.
**Не переводить аккаунт в Pay As You Go** — на Always Free перерасход невозможен в принципе,
а на PAYG можно случайно начать платить.

**2. Это ARM, а не x86.** Пакеты и образы нужны под `arm64`/`aarch64`. Node, Python, Docker
живут нормально, но проприетарные бинарники под x86 (некоторые торговые терминалы,
старые .deb) просто не запустятся. Если новому боту нужен Chromium — ставить `snap install
chromium`, как здесь, а не скачивать сборку Playwright (её ARM-версии может не быть).

**3. Свопа нет.** 20 ГБ свободно — это много, но если новый бот потечёт, ядро убьёт
случайный процесс, и им может оказаться браузер журнала. Поэтому **новому сервису
обязательно задать `MemoryMax=`** в юните, как сделано у `tv-worker` (`MemoryMax=1200M`).
Это главное требование к соседу.

## 4. Правила общежития

**Не трогать чужие службы.** Журнал — боевой, пользователь торгует через него в реальном
времени. Перезапуск `trade-bot` в середине его диалога раньше ломал запись сделки (состояние
теперь переживает перезапуск, но лишний раз не надо).

**Не делать тяжёлых вещей в торговые часы.** Сессии пользователя: с 10:00 до примерно
23:00 по Минску (сервер живёт в UTC, Минск = UTC+3). Сборки, обновления, нагрузочные тесты —
ночью. Если забить все ядра, съёмка скринов начнёт отваливаться по таймауту.

**Занятые ночные окна** — не ставить своё расписание туда:
- `01:00–02:00 UTC` — обновления snap
- `01:00 UTC` — `apt-daily-upgrade`
- `02:30 UTC` — ежесуточный перезапуск браузера (`tv-browser-restart.timer`)

**Не трогать профиль `/home/ubuntu/tv-profile`** — там живёт сессия TradingView, восстановить
её можно только руками через VNC с 2FA пользователя.

**Lingering включён** (`loginctl enable-linger ubuntu`) — не выключать: без него systemd гасит
пользовательский сеанс при выходе из SSH и убивает Chromium журнала. Это стоило суток отладки.

## 5. Как ставить нового бота (проверенный шаблон)

Так сделан журнал, повторяй один в один.

```
~/trade-bot/      — журнал (занято)
~/tv-worker/      — съёмщик (занято)
~/<новый-бот>/    — сюда
```

Юнит `/etc/systemd/system/<имя>.service`:

```ini
[Unit]
Description=<что это>
After=network-online.target

[Service]
User=ubuntu
WorkingDirectory=/home/ubuntu/<новый-бот>
Environment=BOT_MODE=polling
ExecStart=/usr/bin/node bot.js
Restart=always
RestartSec=5
MemoryMax=512M

[Install]
WantedBy=multi-user.target
```

Дальше `sudo systemctl daemon-reload && sudo systemctl enable --now <имя>`.
Деплой кода: `rsync -az -e "ssh -i ~/.ssh/oracle_trading" bot.js ubuntu@130.61.141.38:~/<новый-бот>/`
плюс `sudo systemctl restart <имя>`. Логи: `sudo journalctl -u <имя> -f`.

**Телеграм-бот — только long polling.** Не вебхук: портов наружу нет и открывать их не надо.
У каждого бота свой токен от @BotFather; два процесса с одним токеном получат 409.

### Грабли, которые стоили времени на этом же сервере

- Если опрос Telegram упал, **процесс обязан умереть** (`process.exit(1)`), иначе express
  держит порт, systemd считает службу живой, а бот молчит.
- `handlerTimeout` у Telegraf по умолчанию 90 секунд — длинный обработчик отваливается
  и в режиме polling роняет сам опрос.
- Нельзя дёргать `getUpdates` через curl для проверки — Telegram разорвёт опрос бота.
- Состояние диалога писать на диск, а не держать в памяти: деплой посреди разговора
  с пользователем иначе теряет данные.
- Долгие SSH-команды с Mac рвутся. Запускать через `nohup bash -c "... > /tmp/out" &`
  и забирать результат отдельной командой.

---

## 6. Вывод

Ставить можно. Телеграм-бот без браузера — это десятки мегабайт памяти и почти ноль
процессора, таких тут поместится ещё много.

Осторожнее, если новому боту нужен **свой Chromium**: второй постоянный браузер добавит
примерно ещё одно ядро и 1.5–2 ГБ. Машина выдержит (станет 2 ядра из 4), но запас
сократится заметно. Если браузер нужен не постоянно, а изредка — лучше запускать его
на время задачи и закрывать, а не держать как службу.
